# Zephyr Extension

[简体中文](README.md) | **English**

Build Zephyr firmware with west or CMake, inspect board targets, manage modules, and edit Kconfig and devicetree in VS Code. Open **Zephyr Extension** in the Activity Bar to set up a workspace.

Local paths in the workbench and debug sidebar use `/`, as in `samples/hello_world`. On Windows, the path entry fields also accept `\` when pasting from File Explorer.

Open the **Z chip** in the VS Code Activity Bar. The workbench opens on Workspace. Its tabs are Build, Workspace, Project configuration and Modules. The build method in the header applies to the active project.

**Workspace folders and debugging.** Click **Workspace folder** in the target sidebar to switch projects. Opening a file in a workspace folder or activating a debug session scoped to it also selects that folder. Moving to the workbench or terminal keeps the selection. The sidebar reads the debug runner from the current app and board’s generated `zephyr/runners.yaml` and shows the reason when it is unavailable. Use **Refresh debug target** at the bottom of the list to reread the target.

**Set up missing components.** Under **Workspace → Environment setup**, choose **Set up missing components**. Review the suggestions for west or CMake and select the components you want. Use the package manager or pick an existing tool or offline installer. Detection runs again after each step. Windows offers WinGet when available and MSI/EXE installers. Ubuntu supports APT and DEB packages. macOS supports Homebrew, PKG installers and DMG disk images. Follow the publisher’s instructions inside a mounted image.

**Prepare a computer.** Open **Workspace → Environment setup**. Each host tool offers an installed executable, a supported package-manager action or its official source. Under **Python environment**, use a virtual environment for west and build dependencies. For an offline installation, point to a local wheel directory containing the required dependencies. Under **Source and toolchain**, set `ZEPHYR_SDK_INSTALL_DIR` by choosing an existing SDK or a release bundle for the host, choose its destination and review CMake package registration. Offline SDK installs require the release’s matching `sha256.sum`. Workspaces with a compatible `west sdk` can choose individual GNU toolchains. [Official SDK releases](https://github.com/zephyrproject-rtos/sdk-ng/releases)

**Share an environment setting.** Workspace overrides apply to this project. Under **Build environment → Register variable**, review the host, scope, previous registration and new value. Windows offers current-user and system registrations. On Ubuntu, an `environment.d` registration applies to new systemd user sessions. On macOS it applies to new programs started by launchd in the current login session and expires at logout. [Windows scopes](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_environment_variables) · [Linux session environment](https://www.freedesktop.org/software/systemd/man/latest/environment.d.html) · [Apple launchctl](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchctl.1)

**Move to another computer or folder.** Choose **Extensions → Install from VSIX…** and select the package from any directory. For custom tools, open **Host tools → Tool search directories…** and pick the directory containing the executables. Directories inside the project are stored as workspace-relative paths. External directory selections are private to this workspace on this host. Under **Source and toolchain → Get source…**, select an unpacked source tree, download an official tag or initialize its west workspace. When changing operating systems, select an SDK published for the destination host and recreate the virtual environment and build directory. [Zephyr installation guide](https://docs.zephyrproject.org/latest/develop/getting_started/index.html) · [Python virtual environments](https://docs.python.org/3/library/venv.html#how-venvs-work)

**Discover modules offline.** Select CMake under **Build**, then open **Workspace** to review local modules. The extension recognizes `zephyr/module.yml` or `zephyr/module.yaml`, as well as the legacy pair `zephyr/CMakeLists.txt` and `zephyr/Kconfig`. For modules stored elsewhere, select the module directory under **Modules**. Select the modules your project needs and configure the build. After configuration, **Modules** marks the local modules in the current build, including those added by the application. Check their paths in `zephyr_modules.txt` in the build directory. [Zephyr module rules](https://docs.zephyrproject.org/latest/develop/modules.html#without-west)

**Use a west manifest.** The build, configuration graph and module list share the current workspace’s effective manifest. When an import is unavailable, the interface identifies the partial list. A failed batch retains each module’s result so you can retry unfinished work.

**Choose the SDK for your host.** Start with the release recommended by your checkout. The download list uses assets actually published for the selected release, host OS and architecture. The current Zephyr getting-started guide targets Ubuntu 24.04 LTS or newer and Apple Silicon on macOS. For Ubuntu 22.04 or Intel Macs, verify your checkout’s tool requirements and use a compatible SDK release or an existing toolchain. [Zephyr host requirements](https://docs.zephyrproject.org/latest/develop/getting_started/index.html) · [Official SDK releases](https://github.com/zephyrproject-rtos/sdk-ng/releases)

**Workbench appearance** in the upper right previews the VS Code theme, light or dark colors, and adaptive, compact or comfortable spacing. Apply saves these preferences to VS Code user settings. Escape cancels the preview. Editor zoom and font size are independent.

**Build** starts with a choice of west or CMake. Choose the application, board and build directory, then configure or build. If a prerequisite is missing, use the action beside it. Expand the sections below the target to inspect inputs, outputs, variables and the command preview. The preview lists the task's working directory, executable and each individual argument, including paths containing spaces.

**Flashing firmware.** Open **Build → Firmware flashing** and choose a runner supported by the board. The default comes from `zephyr/runners.yaml`. For sysbuild, review the order from `domains.yaml` or select one image. Expand the list of outputs, check the image, device ID and command, then choose **Flash firmware**. Leave the device ID empty to use the runner’s default. Scan probes with pyOCD, or enter a serial number for other runners that accept a device ID. For CMake projects, **Use workspace task** runs the vendor task defined in the current folder’s `.vscode/tasks.json`. **Probe and driver** checks the host tool. [Zephyr flashing guide](https://docs.zephyrproject.org/latest/develop/west/build-flash-debug.html#flashing-west-flash)

**Inspecting variables**. Workspace shows the environment available to build tasks and where the values came from. To inherit a shell variable, launch VS Code from that environment. On Build, choose an application, board and build directory. Build variables shows the inputs for the next configure alongside the values recorded in that directory’s `CMakeCache.txt`. For example, applying `CMAKE_BUILD_TYPE=MinSizeRel` after configuring with `CMAKE_BUILD_TYPE=Debug` lets you compare the two values. Run Configure to refresh the cache. A new build directory can show the inputs before its first configure.

**Choose a local path.** **Choose directory…** opens VS Code's folder picker. On systems that support it, create a directory in the dialog. **Enter path…** accepts absolute paths or paths relative to the active VS Code folder, such as `build/debug` or `../zephyr-sdk`. A relative path in the operating system's file picker is relative to the folder displayed by that picker. The extension asks before creating a missing build directory. Tools, sources, SDKs and existing modules may live outside the project. A new configuration fragment starts as a draft and is written when you save it to the project.

**Choosing a compiler.** Select a board and CPU under **Build → Build target**, then check **Target compiler**. In Automatic mode, check the recommended compiler’s executable name and path. After configuring, compare it with the compiler CMake recorded. The full paths distinguish tools that have the same filename. To use your own toolchain, apply another candidate or browse for a cross GCC executable. This choice belongs to the current application and board. Candidates marked unverified can still be selected. After configuring, check `CMAKE_C_COMPILER` for the executable Zephyr used. Use a new build directory when changing the compiler of an already configured build. For example, with the Zephyr GNU SDK the Cortex-M4 in `mps2/an386` uses `arm-zephyr-eabi-gcc`. Automatic mode uses your explicit `-D` compiler definitions. Applying another candidate changes the configure command for this application and board. Restore Automatic to use your original definitions again. For an out-of-tree board, add a directory containing `boards/` beneath the board selector. [Zephyr SDK](https://docs.zephyrproject.org/latest/develop/toolchains/zephyr_sdk.html) · [External cross compilers](https://docs.zephyrproject.org/latest/develop/toolchains/other_x_compilers.html)

**Project-owned boards.** Choose **Board and CPU → Use project settings** to inherit `BOARD` from the application, environment or existing build directory. To override it, search the inline list. **Use this BOARD** also accepts an alias or an unlisted revision. Choose a fresh build directory when switching an existing build to a different board.

**Multiple checkouts and board discovery.** When several Zephyr trees share a parent directory, open the intended checkout or an application inside it. If you open their common parent and neither a manifest nor an explicit setting identifies a checkout, select the source in **Workspace**. Check the origin of any existing `ZEPHYR_BASE`. If a build cache belongs to another checkout, choose a fresh build directory. Build and the configuration map share the board picker. Even with no search results, you can enter a full `board[@revision][/SoC/CPU]` and click **Use this BOARD**. **Add board root…** accepts a directory containing `boards/`, the `boards/` directory itself, or a board definition directory beneath it.

**Discovery issues** lists the affected files, parser messages and suggested repairs. Use **Open file** to check YAML indentation, module dependencies, SoC references or manifest paths. Reopen the board picker after fixing the file. For workspace and module discovery, use **Workspace → Environment setup → Detect again**. Independent valid entries can remain available. The selected checkout's Zephyr tools determine whether the actual configuration and build succeed. [Official board target names](https://docs.zephyrproject.org/latest/hardware/porting/board_porting.html) · [Official west board command](https://docs.zephyrproject.org/latest/develop/west/zephyr-cmds.html)

**Multi-image projects.** Enable **Sysbuild** for a fresh build directory, then configure and build. An existing sysbuild root is detected automatically. Build lists the images from `domains.yaml` and marks the main image. The configuration graph reads Kconfig and devicetree from that image. Use a namespaced definition to configure another image, for example `remote_CONFIG_DEBUG_OPTIMIZATIONS=y`. [Zephyr sysbuild](https://docs.zephyrproject.org/latest/build/sysbuild/index.html)

For example, after selecting a `.conf` for the nRF5340 application core, choose **Use project settings** and configure again to restore the project's files. The network core keeps its own inputs. While debugging a core, the sidebar follows that image and the Build page can still build the whole system.

**Selecting build inputs.** After choosing the application and board on **Build**, inspect **Board devicetree**, **Application configuration**, and **Devicetree overlays**. The workbench locates the board DTS and shows the ordered application, SoC, and board fragments selected by Zephyr conventions. A lone nonstandard configuration is suggested for selection. Selecting it supplies `CONF_FILE`. You can configure with multiple candidates or without a board-local DTS. The build record then shows the inputs resolved by Zephyr, including files selected by project CMake logic. [Zephyr configuration file rules](https://docs.zephyrproject.org/latest/build/cmake-ref/module/configuration_files.html)

Use **Choose from list…** to search by filename or path, or **Browse…** to select files on disk. Choose one base DTS or multiple configuration files or overlays. **Merge order…** sets which fragment is applied first. Selections supply `DTS_SOURCE`, `CONF_FILE`, or `DTC_OVERLAY_FILE` for this workspace folder, application, board and build directory. **Use project settings** restores the original definitions or Zephyr discovery. Configure again after changing inputs. The Kconfig and Devicetree branches of the configuration map offer the same selection controls. The devicetree branch also lists the recorded inputs and merged output. [Devicetree overlays](https://docs.zephyrproject.org/latest/build/dts/howtos.html#set-devicetree-overlays)

**Parallel build jobs.** Auto uses the logical processors available on the build host and respects an existing `CMAKE_BUILD_PARALLEL_LEVEL`. Pick a preset, enter a custom count, or select 1 for a serial build. Run Build again to use the new job count. With 4 jobs the preview shows `--parallel 4` for CMake or `-o=-j4` for west. Select the target chip's CPU separately in **Board and CPU**. [west build parallelism](https://docs.zephyrproject.org/latest/develop/west/build-flash-debug.html#build-parallelism)

**Configure Kconfig**. Open **Configure Kconfig** from the extension sidebar or Build. Configure your selected application and board once, then search by symbol or prompt. For example, search for `THREAD_NAME`, choose `CONFIG_THREAD_NAME`, set it to `y` and stage it. Review the diff and destination (such as `prj.conf`), save to the project, and configure again to check the effective value. To explore the native menus and dependencies, open `guiconfig` for a graphical window or `menuconfig` for a terminal. By default those tools save `zephyr/.config` in the build directory. [Zephyr interactive Kconfig interfaces](https://docs.zephyrproject.org/latest/build/kconfig/menuconfig.html)

**Editing a hardware node.** After configuring the build, find the UART in the devicetree branch and check its full node path. Select a status or an editable scalar, such as `current-speed`. To try a baud rate of `57600`, stage the value into an application overlay, then review and save. References and multi-cell values are shown in DTS syntax for inspection. If there was no overlay and you create the default `app.overlay` here, the next configure can rediscover default overlays in a previously configured target. Explicit overlay selections still apply.

**Choosing a fragment.** Kconfig can merge several inputs. The file selector distinguishes relative paths and shows which inputs the last build used, including `EXTRA_CONF_FILE`. When an older build has no record of all inputs, candidates can still be edited. To activate an additional saved fragment, include it in this target and configure again.

**Save a copy or update the project.** **Save a copy** opens the system save dialog for a new `.conf` or `.overlay` file and preserves both the original and the working draft. To update the project, review the destination and write back to the original, or create the file if it is new. If another editor changed the original, save the draft as a copy before resolving the conflict. Configure again to inspect the effective value. When Zephyr has cached an empty default overlay list, creating the first `app.overlay` in the extension lets the next configure rediscover default overlays. Explicit selections and Zephyr’s normal selection order still apply.

**Detect and save local components.** Offline discovery inspects the current folder, common subdirectories, sibling project directories and the west root, if present. It recognizes Zephyr’s CMake package, the SDK version and package configuration, application calls to `find_package(Zephyr)`, and standard module entry points. Explicit settings take priority. Choose between locally detected copies of the same module. Discovery makes modules available for selection. The project determines which are built. Defer saving to use the results for this session, or run detection again. **Save to workspace** updates `zephyrWorkbench.locations`, using relative paths on the same filesystem and preserving other settings.

**Work offline.** Select local sources, an SDK, a Python wheel directory and any modules that the project requires. Review each tool's source and destination before installation.

**Navigating the configuration map.** Use **Locate selected node** beside the search box to bring the selection back to the center. **Fit map to view** shows all expanded branches. Choose **Full-screen configuration** to fill the display or **Configure in new window** for a resizable canvas on a second monitor. Open **Inspector** or **Drafts** along the bottom to edit, compare, save a copy or write back to the project. Use the top-right return button to bring the editor and its drafts back to the original group.

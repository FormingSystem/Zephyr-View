# 工程分析：从应用入口看懂线程、函数和数据流

**简体中文** | [English](thread-analysis.en.md)

设计评审稿，基线为 Zephyr Extension 0.5.18。开发者打开陌生工程时，通常先问「有哪些任务」「这个任务为什么会运行」「它等待谁，又把结果交给谁」。建议工作台增加一个只读的「工程分析」入口，默认展示当前构建镜像的任务关系。从一项任务进入函数细节，连接调试器后可在同一位置查看暂停时的调用栈。[打开交互样例](thread-analysis-preview.html)

## 先走通一例

以 Zephyr v4.2.0 的 `samples/synchronization` 为例。开发者从 `main()` 出发，可以跟到线程 A 的创建和显式启动。工程中还有一个通过 `K_THREAD_DEFINE` 静态定义的线程 B。只从 `main()` 递归追踪普通函数调用会漏掉 B，因此总览要同时列出应用入口和独立注册的执行入口。[示例源码](https://github.com/zephyrproject-rtos/zephyr/blob/v4.2.0/samples/synchronization/src/main.c#L71-L127) · [Zephyr 系统线程](https://docs.zephyrproject.org/latest/kernel/services/threads/system_threads.html)

| 在图里选什么 | 应该看到什么 | 可以据此回答什么 |
| --- | --- | --- |
| 应用入口 `main()` | 创建 A 时传入 `K_FOREVER`，后续调用 `k_thread_start`。另有 B 的静态声明，可跳到声明处 | A 在哪一步具备被调度的条件？B 从哪里来？ |
| 线程 A | 入口调用 `hello_loop`，等待 `thread_a_sem`，调用 `printk`，最后释放 `thread_b_sem` | A 等谁，执行了什么，怎样让 B 有机会往下走？ |
| 线程 B | 同一个 `hello_loop`，两个信号量实参顺序相反 | 为什么相同的函数在两个线程里有不同的输入和输出？ |
| 对象 `thread_b_sem` | 初值 0，上限 1。列出 A 的 give 调用点、B 的 take 调用点和各自入口 | 两个任务之间传的是执行许可。输出的问候文本走控制台 |

线程 A/B 的函数节点均可回到同一个定义。切换任务时保留各自的实参绑定和展开位置。源码能解释二者如何交替；某一次打印发生在哪颗核、何时唤醒，要查看对应运行的记录。[共享函数及调用点](https://github.com/zephyrproject-rtos/zephyr/blob/v4.2.0/samples/synchronization/src/main.c#L36-L99) · [官方示例及预期输出](https://docs.zephyrproject.org/latest/samples/synchronization/README.html)

## 在 VS Code 中怎样浏览

| 层级 | 默认内容 | 操作 |
| --- | --- | --- |
| 工程总览 | 顶部沿用应用、板、镜像；画布放应用入口、已发现的线程和跨任务对象。内核初始化、系统线程、驱动内部默认折叠 | 点线程进入独立视图；点信号量或队列看所有生产者、消费者或等待者；按名称搜索并定位，支持键盘选择 |
| 单线程 | 显示入口、创建或注册位置、启动条件、调用一层，以及输入、输出和可能阻塞的位置 | 单击展开下一层；双击或通过键盘动作打开调用点或定义；选择「调用者」反查。返回总览恢复原焦点 |
| 函数与对象 | 在图下方就地显示签名、按调用点绑定的实参、返回值、对象读写、来源文件及行号 | 从输出跳到使用该对象的另一个线程；多处调用列为清单。递归边和共享函数用回链表示 |
| 调试暂停 | 当前会话、镜像、选中线程和暂停序号；按调试器顺序显示真实栈帧 | 联动 VS Code 原生调用堆栈和源码；选帧按需展开可用变量。恢复执行后结束这次快照的实时状态 |

左侧沿用现有的调试目标与 VS Code 原生调试视图。图、详情在同一编辑器上下排列，窄屏将关系展开为可操作列表。分离到大屏时保留镜像、任务和选中项。常驻「定位当前节点」「适合窗口」「返回」；画布支持空白拖动、Ctrl + 滚轮和键盘缩放。关系线上写动词，来源状态有文字，在深浅和高对比主题下均可判读。

## 什么证据可以画什么边

| 来源 | 允许展示 | 边界与缺失反馈 |
| --- | --- | --- |
| 当前镜像的编译数据库、生成头文件、C/C++ 语义分析 | 实际参与编译的翻译单元、宏展开位置、可解析的直接调用、参数、注册对象；保留源码拼写位置和调用点 | 编译单元可在链接时被裁剪。记录解析覆盖与失败原因；缺构建输入时标为「源码候选」，保留源码浏览。指针调用给出可证明的候选及赋值位置，无法解析时保留未知端点 |
| Zephyr API 的参数语义与实际对象绑定 | 线程创建与启动、任务提交与处理、信号量 give/take、消息队列 put/get、可证实的对象读写 | 带超时的 take/get 表示可能等待。消息队列收发按同一对象关联，多对多时保留所有端点。某次消息实际由谁收到，需要运行证据 |
| 当前 ELF 中可用的符号和调试信息 | 佐证镜像中的符号及地址、将观测帧定位到源码 | 内联、优化、裁剪符号会产生缺口；符号存在本身不能证明函数执行过 |
| VS Code 调试会话的暂停事件和 DAP `threads`、`stackTrace`、`scopes`、`variables` | 适配器在这次暂停中返回的线程、帧和可用变量 | 部分探针只报告 CPU 核或单一执行上下文；保留调试器原名，不能可靠对应 Zephyr 线程时显示「未映射」。同名函数、同名线程不足以建立映射 |
| Zephyr Tracing 或 Thread Analyzer 的已有输出 | 有时间戳的调度、等待和唤醒事件，或者某次观测的栈占用 | 区分声明栈容量、静态估算和运行时高水位；缺事件显示采样间隙。线程分析器的占用统计不能还原函数调用链 |

类型信息与数据方向分别记录。`const T *` 约束这一访问路径，参数名和指针类型本身不能定出业务输入输出。优先使用 API 契约、实际读写表达式和可追踪的实参。比如 `k_msgq_put` 的缓冲区提供消息，成功的 `k_msgq_get` 会写入接收缓冲区；信号量只传递许可。普通函数返回的错误码与具体输出缓冲区分行显示。无调试快照时展示表达式与类型，变量实际值留给调试器。[消息队列](https://docs.zephyrproject.org/latest/kernel/services/data_passing/message_queues.html) · [调试适配器协议](https://microsoft.github.io/debug-adapter-protocol/overview)

中断、定时器和工作队列需要记录执行上下文。例如 ISR 提交 `k_work` 后，由对应工作队列的线程运行处理函数。图中保留「提交 → 工作项 → 处理」和注册位置；切换到处理函数时能看到实际归属的队列。多个工作项可以复用同一处理函数。[Zephyr 工作队列](https://docs.zephyrproject.org/latest/kernel/services/threads/workqueue.html)

## 如何接入独立扩展

1. **确定分析目标。** 复用现有工作区的应用、构建目录和镜像。普通构建读本次构建目录；sysbuild 从 `domains.yaml` 列出镜像并读取所选镜像的编译数据库、配置和 ELF。west 与 CMake 共用入口。切换镜像后立即隔离旧数据。[目标读取](../../extension/target.js) · [镜像枚举](../../extension/sysbuild.js)
2. **收集静态证据。** 按镜像读取 `compile_commands.json` 的工作目录、宏、包含目录、语言和每个文件的编译参数。本地 C/C++ 分析器按需生成语义节点并保留宏调用位置；已有 VS Code 调用层次提供器可补充交互导航，仅在可核实使用同一构建上下文时提升证据等级。版本不兼容、生成头缺失或未配置数据库时，显示受影响文件及可采取的操作。需要导出编译命令时，提供显式的 CMake 配置动作。[Clang 编译数据库](https://clang.llvm.org/docs/JSONCompilationDatabase.html) · [VS Code 调用层次命令](https://code.visualstudio.com/api/references/commands)
3. **把源码语义归入线程。** 函数以镜像和符号标识区分，同名的文件内函数保留各自作用域。每个调用点记录实参与形参的绑定。线程定义、创建点与运行实例分别标识；循环中同一创建点允许产生多个实例。边记录种类、条件、源码范围和依据。对象别名不能唯一解析时列出候选。只对当前关注路径展开，避免递归循环或公共库导致节点数量失控。
4. **接入运行时。** 独立适配层处理调试会话，将会话、暂停、线程、帧和匹配的镜像关联起来。追踪文件额外记录时间基准、CPU、丢失事件和镜像标识；无法校准多个 CPU 的时钟时分别展示。已有 Zephyr 栈分析构建目标、Thread Analyzer 和 Tracing 按版本及产物选用。基础源码分析可以完全离线使用，无须连接目标板或给固件加采样代码。[现有调试入口](../../extension/extension.js) · [Zephyr 构建分析工具](https://docs.zephyrproject.org/latest/develop/optimizations/tools.html) · [Thread Analyzer](https://docs.zephyrproject.org/latest/services/debugging/thread-analyzer.html) · [Tracing](https://docs.zephyrproject.org/latest/services/tracing/index.html)
5. **分开图数据和呈现。** 配置树按单父节点组织，而调用和线程通信允许多父节点和环。单独维护工程分析图，只提取复用拖动、缩放、定位和窗口转移能力。主机依据分析索引中的源码标识打开 URI 和行号。后台分批分析并允许取消，先加载应用入口和线程，再按需进入驱动和内核。切换目标或重建时丢弃过期请求；缓存按镜像、编译参数、源码及所用头文件变化失效。[现有图及视口实现](../configuration-tree.js) · [窗口管理](../../extension/configurationWindow.js)

## 建议的交付顺序与评审门槛

| 顺序 | 可独立验收的能力 | 应验证的工程与失败场景 |
| --- | --- | --- |
| 第一版：离线读工程 | 入口、静态和动态线程、直接调用、信号量与消息队列、调用点输入输出、源码跳转。总览与单线程视图可来回导航 | 用 `hello_world` 验证简单入口，用官方同步示例核对两条线程路径和相反的参数绑定；另用双消费者队列验证多对多。用两个架构、west/CMake、带空格及中文的路径复跑。再用递归、函数指针、多行封装宏和同名静态函数检验未知边与去重 |
| 第二版：调试暂停栈 | 选择会话、线程、帧；定位源码，展开可读变量，恢复后清除过期帧 | 比较能枚举 RTOS 线程与只能报告 CPU 的适配器。核对原生调用堆栈的帧序、优化掉的变量、会话切换和断开。sysbuild 两个镜像含有同名函数时必须准确归属 |
| 后续：异步与时间线 | ISR、工作队列、运行记录与静态关系联动，对照可用的栈占用数据 | 让 ISR 投递工作项并在线程内处理；有意截断一次采样，验证缺口可见。未加 tracing 的固件仍能使用前两层中具备数据的部分 |

建议首先用交互样例回答三个问题：能否找到 B 的启动依据；能否从 A 在等的信号量反查 B 的释放点；能否发现两个线程共用一个函数、等待对象却相反。三项都能从图和紧邻的源码证据回答，再进入真实工程索引的开发。

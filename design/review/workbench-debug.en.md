# Workbench, layout and debug sidebar design review

[简体中文](workbench-debug.md) | **English**

A developer should be able to open one workbench from the Z icon, identify the project and build method, complete setup in the relevant section, and see the target and debugger for that build when debugging. The review follows this sequence. The updated design puts environment setup under Workspace and stacks sections vertically. Earlier screenshots with five navigation entries and side-by-side panels document the original issues.

## Configuration panel width and build entry points

The three build target rows share column widths for labels, current values and actions. Wide panels allocate 14%, 45% and 41% respectively. At intermediate widths values get 76% and actions move below. In narrow panels each field occupies a full row and long paths can wrap. Layout follows the actual panel width, so opening the debug sidebar, splitting an editor, changing display scaling or detaching the window all work the same way. Workspace information, module status and project configuration wrap within their own panels. Icons, control spacing and graph text retain readable sizes.

Build method occupies a row of its own, with `west` and `CMake` as options. A rounded background marks the selected option. Keyboard focus follows its outline. Arrow keys switch the choice and Tab advances to the next control. Native radio semantics expose selection to screen readers. For west, check its executable and the workspace manifest. For CMake, check the application, target and local tools. Each method shows whether configuration and compilation are available. Choosing Build before the target is ready lists all identified prerequisites, with options to choose a board or directory or open the relevant setting. Source, toolchain and modules can also come from the Zephyr CMake package, toolchain files and project declarations. The configure task determines what actually resolves. [Zephyr application development](https://docs.zephyrproject.org/latest/develop/application/index.html) · [Building with west](https://docs.zephyrproject.org/latest/develop/west/build-flash-debug.html)

0.5.5 installation checks covered Chinese and English VS Code on Windows. At editor widths of 1163, 1035, 907, 722, 427 and 251 CSS pixels, the value fields in all three rows had aligned start and end positions, and the first buttons aligned. Long paths and the expanded board list introduced no horizontal overflow. Both routes generated an ELF for `hello_world` and `qemu_cortex_m3`. Build in an empty project showed multiple missing prerequisites. A separate check followed a failed configuration through correction and a successful reconfiguration. | UI-05 Select a target by keyboard | Expand options within the application, board/CPU or build-directory row. Type a fragment to filter, use arrow keys and Enter to select, and Escape to return to the triggering control. VS Code recommends using Activity Bar entries for sidebar views and advises against opening a webview panel directly from them. The agreed design keeps the native target sidebar and also reveals the central workbench on entry. Window restoration, sidebar visibility changes and intentional entry can all trigger the same event, so focus behavior requires particular attention. [VS Code Activity Bar guidelines](https://code.visualstudio.com/api/ux-guidelines/activity-bar)

## Configuration graph and accessibility

| ID and action | Design and rationale | Implementation evidence and checks remaining |
| --- | --- | --- |
| UI-06 Choose a setting on the graph | Application, board/CPU, Kconfig and devicetree nodes should open their corresponding inspector. A click selects; double-click or Enter opens the setting. Dragging the canvas should not select a node. | At the time of this review, the handler rerendered on click, Enter or Space and had no distinct double-click action. Rerender replaces the selected node; verify focus and viewport after switching. The project configuration review covers drafts and saves. [Graph and inspector events](../../extension/media/studioView.js) |
| UI-07 Use a large display or separate window | Provide individual controls for canvas zoom, workbench focus mode and moving to a new window. Application, board, Kconfig, devicetree and draft saving should all remain available there. | In 0.5.8 the graph supported zoom from 50% to 250%. On Windows, Ctrl + wheel zoom from 100% kept the point beneath the mouse stable without resizing the rest of the workbench. Moving to a second native window preserved both staged changes and the selected node’s unstaged input. [Earlier measurements](../review-0.5/README.en.md) · [New window entry point](../../extension/workbench.js) |
| UI-08 Read commands, status and versions | Use a monospace font for commands. Convey state with an icon or text as well as color. Commands and their purposes must remain legible in light, dark and high-contrast themes. | This review fixed low contrast in light-theme command labels. See measurements below. The default theme follows VS Code; manual selection saves an override. Test restoring the default, native high-contrast colors and module status colors separately. [Theme logic](../../extension/media/nativeModules.js) · [Shared styles](../workbench.css) |
| UI-09 Navigate with keyboard and screen reader | Expose current page, selected mode, expanded state and action results. Give icons accessible names, use familiar icons or action verbs, and provide visible focus. Switching language includes accessible labels. | Navigation uses `aria-current`, build mode `aria-pressed`, and status messages `role="status"`. The shared HTML dialog has a hard-coded Chinese close label. Test names, restored focus and action results with a screen reader in both languages; screenshots alone cannot verify them. [Template](../index.html) · [Navigation and mode buttons](../../extension/media/workbench.js) |
| UI-10 Learn from an example | Each tutorial step identifies the target, sample input and visible outcome. Keep mouse movement and click feedback on a 1920×1080 canvas. Scaling and cropping must leave the action visible. | Tested the CMake route with hello_world in the Chinese Windows 0.5.2 extension development host. Typed `mps2an386`, selected `mps2/an386` and checked the target row. The 38-frame, 10.6-second tutorial overlays a pointer, click rings and bilingual captions at the actual click locations. [1080p board-selection tutorial](../../extension/media/guide/board-picker.gif) · [Historical screenshots](../review-0.5/README.en.md) |

**Command-label contrast.** In an isolated installed VS Code workbench on Windows, the reviewer opened Build → Command preview and read the actual foreground and panel background colors. Measurements before and after the shared-style change used the same webview. The light theme originally displayed `#526970` on `#202e34` (2.41:1); inheriting the panel foreground `#d3dfdf` raised it to 10.25:1. The dark theme improved from 8.72:1 to 12.18:1. The AA threshold for normal-sized text is 4.5:1. The measurements cover the command labels only. [W3C minimum text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) · [VS Code webview design guidelines](https://code.visualstudio.com/api/ux-guidelines/webviews)

## Debug sidebar and build metadata

| ID and action | Design and rationale | Implementation evidence and checks remaining |
| --- | --- | --- |
| DBG-01 Locate the debug target | The Zephyr sidebar shows the application, board/CPU, build directory, debug runner and session. The project sidebar and Run and Debug share one data source. VS Code handles variables, watches, breakpoints and the call stack. | Two tree views register the same provider. Workspace, active file, debug session and selected file changes trigger refresh. In a multi-root workspace, check target ownership when returning from a non-Zephyr debug session. [Trees and listeners](../../extension/extension.js) |
| DBG-02 Use shortcut buttons | Show build-directory selection, launch and refresh alongside the target. Frequent actions should remain discoverable when the mouse leaves; users control existing global display preferences. | Three commands are contributed to the native tree title bar, and VS Code controls persistent visibility. The build-directory and session rows are clickable. Refresh had no equivalent persistent inline entry in this baseline. Explain the host setting `workbench.view.alwaysShowHeaderActions` where appropriate, and test persistent entry points under default settings separately. [Command contributions](../../extension/package.json) |
| DBG-03 Check the actual build | Show the board and application from the CMake cache and identify the generated file supplying the runner. Distinguish pending configuration, last successful build and current draft so users can tell which artifact will be debugged. | Reads `CMakeCache.txt` and `debug-runner` in `zephyr/runners.yaml`. A missing value shows a placeholder; invalid YAML produces a message. Build A, select B centrally without configuring, and check that targets remain distinguishable. A sysbuild top-level build also requires per-domain identification. [Target resolution](../../extension/target.js) |
| DBG-04 Select and start debugging | Select the adapter through a VS Code workspace launch configuration. Describe the Zephyr runner and launch configuration separately. Provide the native configuration entry when none exists. | Uses the native picker and `vscode.debug.startDebugging`. Candidates are filtered by `name/type/request`. The baseline did not check the adapter or ELF against the board. Breakpoint, step, continue and stop had not been verified on hardware. Test a workspace with two board targets. [Launch logic](../../extension/extension.js) |
| DBG-05 Check available debugging operations | Show flashing, debugging, attach and other operations according to the current Zephyr build, board and runner. CMake users can use an existing debug adapter and generated ELF. | Inspecting metadata and selecting a launch configuration does not establish support for every runner command or multi-image session. Check the command, runner query results, domain name and generated files, and record tests without hardware separately from physical-board tests. [Zephyr build, flash and debug](https://docs.zephyrproject.org/latest/develop/west/build-flash-debug.html) |

For a debug regression, configure a known runnable test application and generate its ELF. Select its launch configuration from the sidebar, break at the entry function, and check the source file, target ELF, variables and call stack. End the session and check that the sidebar returns to Idle. Record the board, runner or emulator for each Windows and Linux run. The existing evidence does not cover this full sequence. [Native VS Code debugging interface and controls](https://code.visualstudio.com/docs/debugtest/debugging)

The Zephyr View 0.5.24 Activity Bar icon follows the VS Code theme. On Windows 11, selected and unselected icons were checked in Light Modern and Dark Modern. The lowest measured contrast across the four states was 4.88:1. The extension list and details page use the same color artwork.

# Project configuration and module review

[简体中文](configuration-modules.md) | **English**

Project configuration shows which board an application targets, which files take effect and what the user has changed. Modules shows where a component comes from, who needs it, which revision is required and whether the local checkout satisfies it. A manifest can list dozens of repositories, with only some contributing to the current build. Graphs, tables and action buttons should identify their application, workspace and build directory.

This review compares the prototype, the extension's actual message handling and Zephyr's official interfaces. In the tables, **connected** means a UI action reaches the host. Checks on real installations are listed separately. **Partial** indicates a working action with a known gap. **Planned** identifies a design and acceptance criteria. [Workbench interaction design](../interaction.en.md)

| --- | --- | --- |
| C01 Application, board and CPU | **Connected.** Selecting an application or board in the graph opens the target picker in place. Board name, revision, SoC and CPU cluster together identify Zephyr's BOARD target. Application, build directory and board retain independent controls. | C05 Find and edit Kconfig assignments | **Visible menus and fragment editing connected.** Use the current build's menus, types, permitted values and ranges to add, change or remove explicit assignments. | C06 Devicetree nodes and drivers | **Nodes and selected properties connected.** Read paths, hierarchy, labels, aliases, compatible and property values from the build's `zephyr.dts`. | C07 Isolated drafts, review and save | **Per-file drafts connected.** Show original, draft and build value separately. Save As preserves the draft and original. Confirm the change in its generated .config. |

**Basis for review.** Zephyr merges board defaults with application fragments and resolves dependencies and effective values using Kconfig. Explicit assignments, generated values and provenance serve different purposes. Devicetree edits must preserve node identity and overlay order. VS Code picker, diff and keyboard conventions can be reused while Zephyr owns the build results. ## Module sources and synchronization

Selected modules appear above available modules. Each list sorts by name and paginates independently. The initial-letter index sits beside the page controls and includes only initials present in the current result, grouping digits under 0–9 and other initial characters under #. Search applies to the available list. Selections across pages can be synchronized together. Display order is for browsing. Build arguments retain project module order. On Windows, an unsorted manifest of 85 entries was tested: two repositories selected on separate pages synced offline to their target commits. A third, unselected repository kept its original commit. [Modules with the terminal open (1920×1080)](installed/modules-pagination-0.5.11.png)

| M06 Revision and state | **Partial.** Rows distinguish missing downloads, recognized local copies, matches, mismatches and requirements awaiting verification. Compare a fixed SHA with HEAD offline. Check readability in both themes with long English labels. An offline state must not imply the remote is up to date. |
| M07 Download, update and batch sync | **Partial.** Default to the project requirement. An explicit action checks the latest branch head. Resolve a specific SHA in preview before syncing. | M08 Build arguments and undo | **Partial.** CMake passes selected paths to ZEPHYR_MODULES. Uncheck one item, then inspect workspace registration, its directory on disk and default discovery separately. |

**Basis for review.** The west manifest defines projects and expected revisions. Zephyr module metadata defines how modules participate in a build. The tip of a branch may differ from the project requirement. Offer “try latest” and show the target commit and differences in preview. ## Fixes and acceptance scope

- Field-level tests covered explicit n display and preservation, switching to y, removal, duplicate assignment feedback, ordinary comments and existing devicetree status edits. Edits were checked with LF, CRLF and no trailing newline.
- Prioritize evidence for C04–C06 and M01, M05 and M06 before adding controls. The configuration panel should show which file supplied the current value, which dependency constrains it and which input the next build will read.
- Integration testing should cover drafts across two windows, actual Zephyr Kconfig/devicetree reconfiguration, nested manifests, private Git, interrupted batches, Windows/Linux and both themes. The field regression tests did not exercise these cases. Verify each against the relevant row above.


## 0.5.6 Board devicetree and optional overlays

Selecting an application and a fully qualified `BOARD` target is sufficient to configure. The devicetree node should show the board's base description first, the overlays actually used next and the merged `zephyr/zephyr.dts` last. Before first configuration the extension can explain the default rules. Read the actual input sources from the corresponding build directory. The studio creates editing drafts only for user-selected application files. [Zephyr devicetree inputs and outputs](https://docs.zephyrproject.org/latest/build/dts/intro-input-output.html)

| Test scenario | Build result |
| --- | --- |
| `hello_world`, `qemu_cortex_m3`, CMake | Passed only the board target, with no overlay. Zephyr selected `qemu_cortex_m3.dts` and generated `zephyr.dts` and `zephyr.elf`. |
| Same application, board and toolchain, using west build | Used the same board DTS and generated the merged devicetree and ELF. |
| Added `boards/qemu_cortex_m3.overlay` to the application, configured and built in a new directory | Zephyr automatically listed the overlay as the second input. The merged devicetree's `model` matched the overlay. No `DTC_OVERLAY_FILE` was set. |

All three ELFs booted in QEMU and printed `Hello World! qemu_cortex_m3/ti_lm3s6965` to the serial console.

With 0.5.6 installed in Chinese Windows VS Code, the first configuration showed automatic selection by board. After configuration, the base DTS could be opened read-only. Cases with zero overlays and with one automatic overlay each showed the actual inputs. [Default devicetree screenshot (1920×1080)](installed/devicetree-default-0.5.6.png)

## 0.5.7 Board selection and configuration entry points

- After selecting a board, read its detected DTS below Board and CPU. Select the filename to open the source. After configuration, verify the input from the target's build record and expand the row to inspect overlays and the merged result.
- The extension sidebar and Build page both offer Configure Kconfig. The graphical editor targets application configuration fragments. The toolchain's `guiconfig` and `menuconfig` operate on the current build directory. The entry points identify each save location.
- Zephyr IDE's Build Dashboard lets users search symbols, inspect dependencies, edit fragments and run native tools. This extension keeps a vertical layout, uses the options Zephyr resolves for the target and presents changes as drafts that users can apply to a chosen application file. [Zephyr IDE configuration entry](https://zephyr-ide.mylonics.com/reference/configuration/) · [Zephyr interactive configuration](https://docs.zephyrproject.org/latest/build/kconfig/menuconfig.html)

In a Windows test with `hello_world`, selecting `qemu_cortex_m3/ti_lm3s6965` before first configuration displayed `boards/qemu/cortex_m3/qemu_cortex_m3.dts` on the Build page. The file opened read-only. After configuration, the same input was marked build-confirmed. [Devicetree after board selection](installed/devicetree-board-preview-0.5.7.png) · [Build-confirmed devicetree](installed/devicetree-configured-0.5.7.png)

Searching the Kconfig inspector for the prompt `Thread name` found `CONFIG_THREAD_NAME`, which was absent from the original application fragment. Changing `n` to a draft `y` left the original untouched until saving. After reconfiguration and build, generated `.config` contained `CONFIG_THREAD_NAME=y` and an ELF was produced. Separate west and CMake runs launched the official `guiconfig` and `menuconfig`. [Setting and draft](installed/kconfig-symbol-draft-0.5.7.png)

## 0.5.8 Interactive project configuration graph

Expand the application root. Beside a node, inspect its build value, choose a replacement and select the project fragment to receive the edit. Left-drag the background to reach offscreen branches. Ctrl + wheel zooms the graph around the pointer. Long menu titles expand to fit, node paths are abbreviated and the editor shows the specific object.

| Acceptance action | Observation |
| --- | --- |
| Expand Kconfig, pan and zoom in Windows VS Code | The first-level Kconfig branch on qemu_cortex_m3 showed 20 child items after expansion. Panning brought offscreen nodes into view. The ordinary wheel scrolls and Ctrl + wheel zooms around the pointer. A separate window and dark theme were also tested. |
| Double-click a symbol to edit configuration | Set `CONFIG_THREAD_NAME` to `y`. Staging and saving a copy preserved the original contents. After writing back and reconfiguring, the effective value was y. Canceling Save As or encountering a name collision preserved the original. After an external change, the draft could still be saved as a copy. |
| Double-click an actual peripheral to edit a property | Disabled `/soc/gpio@40026000`, reconfigured and verified the change in final `zephyr.dts`. On the same board, set `/soc/uart@4000e000`'s `current-speed` to 57600. Creating the default overlay triggered rediscovery. The effective hardware value and ELF were verified. |
| Add extra configuration to a multi-fragment application | Both CMake and west for `mps2/an386` used the newly registered .conf and .overlay, preserving the original fragment order. Current Zephyr 4.5 splits relative fragment names containing spaces. The extension warns before adding one. |
| Complex hardware configuration | The graph displays DTS expressions for multi-cell properties and phandles. The editor handles status, existing single strings and ordinary 32-bit cells. Binding-specific enums and compound configurations such as pinctrl still need a project overlay. |

Staged `CONFIG_ASSERT=y` on a node, then selected `n` in the same control without committing it. After moving into a second native VS Code window, the draft still read y, the control still read n and the on-disk file matched its original contents.

The board-selection regression started with an existing `qemu_cortex_m3` build, switched to `qemu_x86/atom` in the graph and returned. The previously resolved board directory was used only to verify the original board source. The other board's graph excluded the original board's draft. Returning restored the editable draft.

After writing back both graphical edits, the Windows test recompiled the application and ran the SDK's QEMU. The terminal printed `Hello World! qemu_cortex_m3/ti_lm3s6965`.

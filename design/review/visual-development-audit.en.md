# Visual development requirements review

**Baseline: 0.5.26 at `cb40367`.** The graph can already change the stack and priority of two threads and the parameters of one concurrency object. The generated samples build and run. Developers still cannot draw a third thread or connect two queues into a processing pipeline. That is the first gap for a dedicated programming surface. ## Acceptance path for a dedicated programming canvas

Use three threads to exercise program design. A sampler sends to queue A. A processing thread receives from A before sending to B. A display thread receives from B. Start from a small example or build the graph by adding and removing threads and objects.

1. Select threads, kernel objects and directed operations. Show the corresponding Zephyr API and the order within each thread beside the graph. A queue send copies a payload, a semaphore transfers a permit, and a mutex protects a shared resource. The three relationships should communicate these different contracts. [Message queues](https://docs.zephyrproject.org/latest/kernel/services/data_passing/message_queues.html) · [Semaphores](https://docs.zephyrproject.org/latest/kernel/services/synchronization/semaphores.html) · [Mutexes](https://docs.zephyrproject.org/latest/kernel/services/synchronization/mutexes.html)
2. Reconnect a send from A to B and reorder operations in the processing thread. Check the object arguments, calls and order in the C preview. Try duplicate names, references to removed objects and a message operation on a semaphore. Check that problems are identified at their source and prevent invalid export.
3. Save a graph copy, close it and reopen it. Compare threads, objects, parameter values, references and ordered operations. Modify the copy and check the original. Export into a new application directory. Verify that a destination containing an earlier, hand-edited application is protected.
4. Restore a runnable graph, build it through the existing CMake or west workflow, observe emulator output, and inspect the actual values at a breakpoint. Arrows in the preview express calls. Operations have a local order within their own thread. Use execution evidence for inter-thread scheduling order.
5. Follow the same workflow at 1920×1080 and in a narrow editor. Common actions should be discoverable beside their objects. Collapsing code or properties should release space for the graph. Use pan, zoom and recenter to recover an off-screen selection. Verify the dedicated editor page and separate desktop window individually.

When adding FIFOs, events or work queues, specify ownership, blocking conditions and callback context, and exercise each with a runnable example. Keep the standard generated Zephyr entry points usable by teammates who build, debug and read the C without the graph editor.

## Visual programming and execution playback

The program editor places the component library on the left, the diagram in the center and the inspector on the right. Start at `main`, a thread, a function or a kernel object, then follow the selected function through conditionals, loops and calls. The inspector shows context, parameters and the corresponding C source. Queue arrows follow data, while semaphore arrows follow permits. Driver steps call an adapter implemented in C. Devicetree and Kconfig belong in the project configuration editor.

The recorded example ran on `mps2/an386` under QEMU. A static thread sends 42 to a queue. The receiver enters the conditional path in `scale` and computes 84. The program and console share fingerprint `d6617b87ac27451a`. The current v2 capture has 18 events, including `relay` entering `scale` with 42 and returning with 84. The historical v1 capture has 17 events and records this call only on return. Open the interactive example to replay the execution or step through individual operations and their C source. Playback speed sets the display interval. Without timestamps or sequence numbers, the capture cannot establish elapsed times or count losses that the logger did not report. [Interactive example](visual-program.html?example=firmware&lang=en) · [Program graph](../../extension/examples/visual-program/graph.json) · [Current console capture](../../extension/examples/visual-program/console.txt) · [Historical console capture](../../tests/fixtures/visual-program/v1-console.txt)

An installed VSIX in an isolated VS Code profile was used to select `relay`, open the `scale` control flow, locate its C function, open the firmware example in its own editor, step through send and receive values, and resume playback. The first capture exposed overlapping labels on the queue, call, semaphore and mutex edges. We staggered labels in the same column and checked all four edges in the installed build. The 1920×1080 recording shows the mouse movements and includes bilingual captions. [Watch the 20-second walkthrough](../../extension/guides/media/visual-program.gif)

## 0.5.28 concurrent program editing and source review

| Review item | What to check in the designer |
| --- | --- |
| Connect and arrange | Selecting a thread and queue in opposite orders proposes send or receive. Check the operation and API before committing the connection. Move an existing step and its nested branches to another thread, function or conditional block. |
| Accesses and waits | Select an object or access step to see the calling contexts. Remove the queue's sole reachable sender and follow the finding to the waiting receiver. A send in an uncalled function cannot satisfy it. Check branches, other threads and external C against execution evidence. |
| Source review | Open the exported design and compare the current C with the proposed C before applying it. Local edits and changes since review keep the existing source intact. Opening an actual project file selects the step's line when the source matches. |

The walkthrough was recorded in the installed extension at 1920×1080 with the pointer visible and captions in both languages.

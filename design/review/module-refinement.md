# 构建页之后的模块评审

**简体中文** | [English](module-refinement.en.md)

第一项交付是构建页。第二项处理了工作区与调试侧栏的目标归属（W1、D1），在 Windows 的独立 VS Code 开发宿主完成了双根实测。两项模块同步问题仍保留初次评审的离线复现记录。以下各项分别列出完成范围与待测条件。

## 整改次序

| 次序 | 先处理的用户动作 | 交付边界 |
| --- | --- | --- |
| 1 · 构建 | 选择应用与板、配置、构建，确认可用工具和实际输入 | 以当前构建专项验收为准。下列工作各自评审、各自提交。 |
| 2 · 工作区、清单和模块 | 切换目标后看运行器，查清单中的导入项目，恢复中断的同步 | 优先解决读错目标、漏项和无法判断已执行哪些操作的问题。 |
| 3 · 环境和调试 | 首次搭建，处理多个本地候选，在多根工作区选择调试工程 | 在实际执行操作的页面交代作用范围和缺项，保留原生目录选择与调试视图。 |
| 4 · 工程配置与个性化 | 找到配置节点，区分草稿和构建结果，调整主题与侧栏 | 复用已验收的图、保存和构建接口，再压缩重复展示。 |

## 工作区与环境

| 位置与复现 | 使用影响与修改方向 | 验收条件 |
| --- | --- | --- |
| **W1 · 高 · 已修复并回归。** 在「工作区 → 环境搭建 → 烧录与调试」和调试侧栏查看运行器。两处按当前应用、板和构建目录核对缓存及生成记录；如果运行器文件记录了板目录，也核对它与 `BOARD_DIR` 是否一致。 | 真实 `hello_world`、`mps2/an386` 构建显示 `pyocd`。保留构建目录、改选 `qemu_cortex_m3` 后，原运行器消失，状态说明目录属于其他目标。记录不存在、格式无效、未指定默认调试运行器、上次配置失败时分别说明原因。 | Windows VS Code 1.147.0 的独立开发宿主已验证上述换板过程。自动回归覆盖切应用、失败后重新配置、仅有缓存、板目录矛盾、损坏及空的 `runners.yaml`。该行显示 Zephyr 生成的默认调试运行器；连接探针仍须用实际硬件验证。 |
| **W2 · 中 · 代码确认。** 在空目录打开工作区，查看缺少的 CMake、Python、SDK，再展开 west 工作区。当前正式入口可选已存在的工具、源码、SDK 与工作区；空工作区没有从清单初始化的操作。 | 已离线准备好工具的用户可以继续。首次搭建的用户到缺项为止，无法在该页完成预期的初始化。保留本地指定路径，把“使用现有环境”和“准备缺失组件”放到同一缺项附近。初始化要显示目标目录、清单和将执行的官方命令。 | 三种环境分别验收：已有离线 SDK 和工具，允许联网的新目录，只有源码与 CMake 的应用。前者断网完成配置，第二种在空目录初始化并核对 `.west/config`，第三种全程无需建立 west 工作区。安装包导入只有接入真实执行和结果核验后才标完成。 |
| **W3 · 中 · 代码确认。** 在同一目录放唯一可识别的源码、SDK 和两个应用。识别结果均可查看，但“保存到工作区”要等所有组均选定。 | 只想保存 SDK 的用户也必须先决定用哪个应用。按对象提供“采用”和“保存”，保留整组保存；显示本次采用、工作区保存与进程继承的区别。 | 保存 SDK 时，两个应用仍可待选。检查设置差异只有 SDK 改变；重开、另切工作区后，来源和生效范围正确。原有显式设置优先。 |

## 模块与版本

| 位置与复现 | 使用影响与修改方向 | 验收条件 |
| --- | --- | --- |
| **M1 · 高 · 本轮实测。** 本地 west 工作区的主清单没有直接项目，通过 `self.import: imported.yml` 引入 `imported-module`。离线运行 `west list -f "{name}"` 得到 `manifest`、`imported-module`；工程图使用的直接清单读取与 `modules.entries` 得到空列表。模块页单独调用 `west list`。 | 在模块页能找到的项目，到配置图中可能消失。为同一工作区复用一次有效清单结果；回退到直接读取时，在清单附近给出“直接声明 / 导入尚未解析”和原因。west 项目和有构建入口的 Zephyr 模块仍须区分。 | 含自导入和项目导入的工作区，在模块页与配置图核对相同项目、路径、revision。停用 west、移走导入文件或换工作区后可判断信息来源，旧缓存不串用。local、个人 Git 和官方来源仍能被添加。 |
| **M2 · 高 · 本轮实测。** 两个本地 Git 检出均位于 A，目标 B 的对象已在本机。给第二个检出留一处未提交修改，再离线应用批量计划。实际结果为第一个已切到 B，第二个仍在 A；宿主报告工作树有修改，界面关闭计划。 | 用户得不到已完成模块的清单，也无法在原处只重试失败项。执行前检查每项明显冲突，执行后保留逐项结果、原提交、目标提交和重试入口。已经成功的检出应能立即用于后续操作。 | 用上述两个检出重跑。若第二项在预检后才改变，结果依然逐项准确。处理修改后重试仅执行余项，不更改用户清单中的 revision，成功项不重复下载。 |
| **M3 · 中 · 代码确认。** 新工作区选择应用与板后，模块勾选来自该模式的已保存选择；列表汇总直接清单、额外仓库和本地发现的入口。清单中的项目没有统一的“谁要求它”证据字段。 | 清单列出了可取得的项目，用户仍难以解释这次构建需要哪些。将“清单提供”“配置或模块声明要求”“用户选择”分别标在同一条目上。只在当前 Zephyr 版本及所选目标有可追踪依据时自动采用。 | 准备两个使用不同板或模块配置的应用，逐项核对来源文件、目标修订和选中理由。没有声明依据的项留作候选。对 HC32 工程以其实际清单和本机 Zephyr 源码核对，不能把某一版本里 `cmsis` 与 `cmsis_6` 的关系推广到所有工程。 |

## 工程配置图

0.5.8 的 Windows 安装验收已记录画布拖动与缩放、节点编辑、另存副本以及移动到独立窗口后保留草稿。CMake 和 west 的实测也确认，两种构建方式都采用了登记的额外片段。板级 DTS 可以自动选取，常规应用无需另填 overlay。硬件编辑应继续写入应用片段，最后由构建生成的 `zephyr.dts` 核对。[0.5.8 配置图实测](configuration-modules.md#058-可交互工程配置图) · [设备树与覆盖文件](https://docs.zephyrproject.org/latest/build/dts/howtos.html)

| 位置与复现 | 使用影响与修改方向 | 验收条件 |
| --- | --- | --- |
| **C1 · 中 · 代码确认。** 在有大量 Kconfig 符号的目标里用画布搜索框输入 `CONFIG_`。匹配使用连续子串，结果仅渲染前 40 项；输入离散字符时，行为与选板框的模糊匹配不同。 | 用户可能以为某符号没有被发现。让搜索反馈区显示总匹配数、已显示数和继续查看的途径；使用同一套键盘与模糊搜索习惯。菜单层级、节点路径和别名仍可精确命中。 | 选定第 41 项之后的实际符号，通过搜索、键盘选择和回车打开。再用两个同名外设实例按完整路径区分；窄屏下结果和编辑目标均可读。 |
| **C2 · 中 · 已有实测；复杂类型待验。** 在图中编辑 UART 的 `current-speed` 和 `status`，再对照 phandle、pinctrl 或多单元属性。前两种有已验证的图形编辑；后者呈现构建记录。 | 在属性旁说明可编辑范围，复杂类型给出确切的绑定或片段入口。新增控件必须验证绑定的取值、引用和单元数量。保持工程草稿与板文件、合并结果的边界。 | 单字符串、单 32 位单元和状态各保存并重新配置，核对最终属性。遇到不支持的复杂类型，可查看原值且不会生成有损覆盖。测试覆盖相同属性出现在两个片段的情况。 |
| **C3 · 中 · 待安装态回归。** 在 A 板暂存 Kconfig 和设备树修改，切到同应用的 B 板，再回到 A。随后在有草稿时跨原生窗口、返回或关闭配置页。 | 移窗已有实测，应清楚区分“移动当前配置页”与“关闭编辑器”。待验证的风险是用户在真正关闭页面时是否知道有未写入的修改。 | A/B 和不同构建目录的草稿各有归属；每次保存前显示文件与目标。移动窗口保留两种草稿；关页后对草稿的实际处理与界面提示一致。外部改写时允许另存副本，并保留磁盘新内容。 |

## VS Code 左栏、调试与自定义

| 位置与复现 | 使用影响与修改方向 | 验收条件 |
| --- | --- | --- |
| **D1 · 高 · 已修复，双根宿主实测通过。** 左栏在多根工作区增加「工作区文件夹」选择。打开根内文件、主动选根或激活归属于该根的调试会话均会切换工程。进入中央工作台或终端保留最近的工程。 | 工作台、侧栏和调试启动共用该工程。悬停可核对根的完整路径。无归属的会话不接管构建目录；选调试配置期间切到另一工程会取消原启动操作。 | 实测 A 编辑器 → B 编辑器 → B 工作台 → 终端 → A 编辑器，各阶段的板和运行器均符合实际工程。另在 A 当前时启动属于 B 的 VS Code JavaScript 调试会话，侧栏转为 B，结束会话后仍为 B。自动回归另测原生选择命令路由、无归属会话及调试选择框内切根。 |
| **D2 · 中 · 代码及既有评审确认。** 关闭 VS Code 的 `workbench.view.alwaysShowHeaderActions` 设置，再把指针从目标栏标题移开。选择构建目录、启动和刷新注册在原生标题栏；前两者还有可点击行，刷新没有等价常驻行。 | 常用动作可发现性取决于全局偏好。为确有需要的操作增加紧凑、可聚焦的本视图入口，使用熟悉的 VS Code 图标和中英文名称。不要替用户改全局设置。 | 默认设置、始终显示设置和键盘操作分别测试。指针移开后仍能直接找到刷新、选择目标和启动，同一动作只执行一次，不增加横向滚动。 |
| **X1 · 中 · 外观已实现，模块错误翻译待办。** 右上「工作台外观」已提供跟随 VS Code、浅色、深色，手动选择后可以恢复跟随。模块宿主仍有失败提示直接使用中文。 | 外观控件支持预览、应用和取消。后续按当前语言呈现模块操作失败及恢复方法，保留路径、提交与 Git 原始诊断。 | 外观支持恢复跟随；浅色、深色、高对比主题的可读性与键盘焦点持续随界面回归。模块部分需在中英文各执行一次空模块目录和脏检出失败流程，核对两处提示后再关闭。 |
| **X2 · 中 · 作用域核对。** 在同一 west 工作区里选择模块，再切换应用、板和构建目录。模块选择以 west 根为范围；切到 CMake 后按应用保存选择。相比之下，额外 Kconfig / DTS 片段属于工作区、应用、板和构建目录的组合。 | 保留这几种不同作用域，在操作旁用具体对象提示，例如“用于此 west 工作区”或“用于此板的构建目录”。主题、缩放等个人显示偏好应与会进入构建命令的工程设置分别恢复。 | 从 A 切到 B 和第二个构建目录，再切回 A，逐项比对原模块选择、额外片段、实际命令和界面提示。恢复显示偏好后，工程输入没有变化。 |

## 复验交付

每项变更记录执行平台、语言、输入工程、板名、构建目录、实际动作和结果。桌面截图使用 1920×1080，同一张图同时看得见目标与操作结果。安装态以真实 VSIX 运行；纯数据回归和原型截图另记。真机探针、Linux 安装包流程及私有远端凭据仍需各自环境验收。完成某一项时更新对应专项页、用户手册与本表，不提前关闭其他项。

**English summary.** The build screen was followed by the workspace and sidebar target fixes. A Windows VS Code 1.147.0 development host with two workspace folders retained the selected project across webview and terminal focus. An actual debug session selected its owning folder and left it active after termination. A real `mps2/an386` build reported its generated `pyocd` runner until a different board was selected. The appearance dialog can restore VS Code theme tracking. Module error localization, imported project visibility and recovery from partial synchronization remain open.

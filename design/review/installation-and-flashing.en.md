The review covers the four pages of the installed extension, the Activity Bar and debug sidebar, host commands, actual file and task invocations, and the browser prototype. ## Two workflows

1. **Set up a new computer.** Open Workspace, discover existing components, then choose Install, Official download or an existing local package in the missing component’s row. Review the version, directory and scope, install and check again. Open the vendor’s distribution page when a license, sign-in or interactive-only installer is required. If a package manager or driver only supports a system location, state the restriction and omit the destination picker. SDK installation and project builds can independently use west or local tools. Offline inputs must match the host and target. [Zephyr installation guide](https://docs.zephyrproject.org/latest/develop/getting_started/index.html) · [SDK installation and registration](https://docs.zephyrproject.org/latest/develop/toolchains/zephyr_sdk.html) · [Official SDK releases](https://github.com/zephyrproject-rtos/sdk-ng/releases)
2. **Connect a board.** On Build, read the current build directory, choose the firmware domain or whole system, then choose the board’s default flash runner or another supported runner. Select a probe serial number or serial port as needed, verify the artifact and flash. For multiple domains, respect `flash_order` from `domains.yaml`. The local nRF5340 sample’s main domain is `hello_world`, but flashing starts with `remote` and ends with `hello_world`. A CMake build can use an existing west installation for flashing. When west is absent, offer a verified native method, project task or artifact. Present full-chip erase separately from ordinary flashing. [Zephyr flashing and runners](https://docs.zephyrproject.org/latest/develop/west/build-flash-debug.html#flashing-west-flash) · [Official host tool index](https://docs.zephyrproject.org/latest/develop/flash_debug/host-tools.html)

## Device and system integration

| Detected condition | Next step in the UI |
| --- | --- |
| SDK already installed or in a custom location | Verify the version and compiler and offer reuse. Explain the distinct effects of `ZEPHYR_SDK_INSTALL_DIR`, SDK CMake package registration and `west zephyr-export` for the source checkout. [CMake package registration](https://docs.zephyrproject.org/latest/build/zephyr_cmake_package.html) |
| CMSIS-DAP | Distinguish the probe interface, pyOCD executable and chip support pack. Version 1 commonly uses HID and version 2 WinUSB. On Linux, use actual access errors to guide udev configuration. [pyOCD probes](https://pyocd.io/docs/debug_probes.html) · [Installation and permissions](https://pyocd.io/docs/installing.html) |
| ST-LINK or J-Link | Link to the official tools and drivers from ST or SEGGER. Reuse accessible devices; distinguish multiple probes by serial number. [ST-LINK Windows driver](https://www.st.com/en/development-tools/stsw-link009.html) · [J-Link software](https://www.segger.com/downloads/jlink/) |
| DFU, serial port or emulator | For DFU, check mode, device and interface. A visible serial port establishes that the interface exists; verify the target bootloader. For emulated boards, show available emulation actions first. Distinguish a missing USB device, a busy device and access denied. [dfu-util](https://dfu-util.sourceforge.net/dfu-util.1.html) |
| User, system or remote host | Identify the host that will execute the action. Check persistent variables in a new process. On Windows read and write User/Machine scopes separately. On Linux identify the affected login session. Use the OS authorization flow to install drivers and provide a way to resume after cancellation. [Windows environment scopes](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_environment_variables) · [Linux user-session environment](https://www.freedesktop.org/software/systemd/man/latest/environment.d.html) |

## Acceptance checks

- **Installation.** Cover an existing SDK, an empty directory, a local package, missing target architecture components, vendor web distribution, cancellation and system-managed install locations. Report Ready only after discovering an actual version or executable.
- **Flashing.** Cover a single board with several runners, two domains with differing default order, debug-only runners, missing flash runners, CMake without west, multiple serial numbers and cancellation. Record command-generation tests separately from writes to physical hardware.
- **All pages.** Switch across all four pages using the same application and board. Include multi-root workspaces, narrow windows, Chinese and English, keyboard input, and light and dark themes. After changing an option, verify that original project data and unapplied choices remain traceable.
- **Modules.** For a manifest with imports, compare the graph and module page. When item two in a batch fails, the first must remain marked complete and only unfinished work should retry. The debug sidebar must still offer refresh when Always Show Header Actions is off.

## 0.5.16 delivery and verification

| Module | Changes and results |
| --- | --- |
| Host tools and SDK | Each Workspace tool row offers local installation, an existing file or an official source. Offline SDK tests used a small archive with a SHA-256 manifest, checked integrity and covered failed installation followed by retry in the same directory. Offline Python tests installed a local wheel into an isolated virtual environment. |
| Environment and probes | Workspace retains project settings. When registering at user or system scope, select variables and preview their previous values. The Windows test queried the current user environment and Plug and Play devices. No matching CMSIS-DAP probe was present; the UI provided rescan, driver guidance and official links. |
| Build and flash | Built an ARM example with CMake and produced an ELF on a host without west. Reading real nRF5340 dual-core artifacts produced the full-system preview in network-core `remote`, then application-core `hello_world` order. Checked previews with the default probe and an explicit device ID in the native UI for `mps2/an386`. [Offline build test](../../tests/integration/no-west-build.cjs) · [Multi-domain flash preview](../../tests/integration/flash-preview.cjs) |
| Project configuration, modules and sidebar | Leaf nodes select modules in place; the fragment inspector follows the selection; refresh has a persistent sidebar row. A real workspace resolved 69 modules. A standalone offline example read the pinned revision from an imported manifest. A two-item regression confirmed that after the first item succeeds and the second fails, retry processes only unfinished items. |
| UI | Opened the workbench in English and Chinese in Windows VS Code after VSIX installation. At 506 CSS pixels all four pages remained reachable and the page did not overflow horizontally. Testing exposed a Sysbuild checkbox that left the flash panel loading. After the fix and reinstall, the panel showed the images and command. In English Dark Modern, the lowest measured flash-panel text contrast was 4.53:1. Tab moved from device ID to Scan, and from Flash to project tasks. |

All 145 JavaScript tests passed. On Windows, 11 of 13 Python tests passed and two were skipped for that platform. Linux desktop installation, system-level installation, vendor driver installation, downloading the full official SDK and writing to a board with a probe still required the corresponding environments. Dual-core flashing was verified through actual artifacts and generated commands.

## Probe and driver list in 0.5.22

Opening the group shows each probe’s executable path and device status. Opening it from Flashing focuses the row for the selected runner. Choose an installation folder, deploy the tool or open vendor guidance in that row. USB enumeration and tool discovery run independently. If a selected executable disappears, the row keeps the selection and offers a way to repair it.

Windows checks covered opening and refreshing the installed view, distinguishing the SEGGER commander from Java’s linker, and downloading dfu-util and running its version command. The VSIX includes Linux USB access rules. Installing system drivers on Windows, installing system rules on Linux and programming physical hardware still require hardware acceptance.

# Workspace, environment setup and build review

[简体中文](environment-workspace-build.md) | **English**

Work down the **Workspace** page. Confirm the open folder, select host tools, Python, Zephyr sources and the toolchain, and check the values passed to the build process. The optional west workspace and manifest appear below. Use **Build** to select the application, board and CPU, build directory and build method. Each setting shows its effective source. Edit, restore inheritance or rescan beside the setting. Existing projects can start on the Build page.

This review identifies working host features, example actions in the browser prototype and outstanding work. The tables describe acceptance checks. The results section records the checks performed. Project files and commands refer to the user's current checkout.

For automatic discovery, saving detected settings, native selection dialogs and path resolution, see [Local selection and discovery](local-selection.en.md).

## 0.5.10 Target compiler

Find **Target compiler** below Board and CPU on the Build page, or inspect the same target in the toolchain group under Workspace → Environment setup. Automatic mode follows the project and Zephyr. Before configuration, the board metadata supplies architecture evidence. After configuration, check `.config` and the compiler recorded by CMake. Applying a candidate manually binds it to the current workspace folder, application and board. Original project arguments remain available when automatic selection is restored. When changing the compiler for an existing target, use a new build directory to retain the old build for comparison.

| Windows acceptance case | Observation |
| --- | --- |
| CMake, Cortex-M3 | With no explicit SDK directory, discovery found the ARM GNU compiler in a CMake-registered SDK. After configuration, the test checked `CMAKE_C_COMPILER` and generated an ARM ELF. |
| west, `qemu_x86/atom` | The local SDK provided `x86_64-zephyr-elf-gcc`. Zephyr selected 32-bit target options for the board and produced an i386 ELF. |
| External GNU toolchain | A separate ARM Embedded GCC installation configured and built the application. The CMake cache pointed to the external executable. |
| Out-of-tree board | Selecting the custom root or its `boards/` directory allowed both discovery and a real build to find the board. Additional roots can be removed individually. Process and project roots remain in the search path. |

## Interaction review sequence

1. Open the workspace in a narrow viewport and on a 1920 × 1080 desktop. Switch through the four environment categories. Read the category, effective value and source in the same column. Switch languages and themes. Long paths should stay clear of buttons and reveal their full value on focus.
2. Prepare two build directories for the same local project. Select the same application and target in west and CMake. Compare commands and artifacts. Change just one board or environment setting at a time and trace it through the command, cache and output.
3. In a fresh temporary directory, try read-only checks, initialization, offline dependency installation and disassociation. Identify prototype-only operations in the acceptance record. Prototype fixture data does not demonstrate host execution.

### Variable values and provenance

| Action | Expected result |
| --- | --- |
| Inspect `ZEPHYR_BASE` in Workspace, temporarily apply the detected value, then save it to the workspace | The full path is readable each time. The source identifies the original source, temporary detection or saved setting. A variable available only in cache still says the process has no value. |
| Add `MY_OPTION:BOOL=OFF` under Build variables. After configuring, change it to `ON` | The pending value shows `ON`. The target cache retains `BOOL` and `OFF`. The preview shows the inputs for the next configuration. |
| Set `COUNT=0` and `EMPTY=` individually, then switch to a new build directory | Both explicit values are readable. The new directory reports no cached value. The old cache remains associated with its target. |

## Results from this review

On Windows, the extension's build plan drove real CMake in a temporary directory containing spaces. A new tree used `CMAKE_GENERATOR=Ninja Multi-Config`. After removing the environment variable and reconfiguring and building the same directory, the cache retained Ninja Multi-Config. In a second fresh directory without an explicit generator, both configuration and build used Ninja. The test also checked that west arguments were free of CMake's `-G`. A small CMake project that required no compiler isolated generator behavior.

On the same machine, the official `samples/hello_world` and `qemu_cortex_m3` used local Zephyr 4.5.0-rc1, Zephyr SDK 1.0.1, an existing Python virtual environment and local modules. The extension's `describe` generated task arguments for one temporary west build tree and one CMake tree. Both configured, compiled and produced `zephyr/zephyr.elf`. The test supplied simulated VS Code path and state inputs and invoked actual local tools. Board execution, QEMU, debugging and a Linux rerun were outside this round.

BUILD-07 also used two temporary applications. A's cache included a custom configuration, generated devicetree and ELF. Switching to B showed only B's inputs. Explicit typed `CONF_FILE:STRING` and `DTC_OVERLAY_FILE` opened the corresponding files for B. Switching only the board also hid old artifacts. A's configuration, CMake cache and generated files matched their pre-test contents.

## 0.5.9 Build workflow

The previous version was measured in a 1920×1080 VS Code window with a 763-pixel-high editor area. At 1163 pixels wide, the page was 1837 pixels tall and the command preview began at pixel 1614. A 620-pixel split still required scrolling past a separate Project actions panel to reach the preview. Directory buttons and long paths competed for space on the same row.

| Action | Design decision and acceptance check |
| --- | --- |
| Choose method and target | west and CMake share a row of radio controls with arrow-key navigation. Then choose application, board and build directory. Overwide field groups wrap as units, keeping argument labels and button text whole. |
| Configure, build and troubleshoot | Place actions below the target. Show missing prerequisites and available remedies per action. Retain the target, exit status and link to task output on build failure. |
| Verify what will run | The command disclosure shows the actual working directory, program and individual arguments. When running from the application root, show `.` as its short path. Check arguments with spaces, quotes, empty values and values marked sensitive separately. |
| Compare arguments, files and artifacts | Collapse secondary information by purpose. During host refresh retain expanded sections, unapplied arguments, caret and active search candidates. Refresh must not select a board. |
| Customize and resize | Three density settings share CSS variables. Preview density and theme in the title bar and apply them to VS Code user settings. Browser and extension reuse the same controls. The host runs real tasks. |

When following the host theme, use its editor, button, border and focus colors. Inspect text, selection and keyboard navigation in standard and high-contrast themes. [VS Code webview design guide](https://code.visualstudio.com/api/ux-guidelines/webviews) · [Webview theme API](https://code.visualstudio.com/api/extension-guides/webview#theming-webview-content)

### Checks with the installed extension

Two layouts used the same `hello_world` project in a 1920×1080 Windows VS Code window. The Chinese light workbench had 1178×763 CSS pixels and the English dark split editor had 590×763. Closing secondary sections made the content fit exactly, without horizontal or vertical overflow in either. The three actions on the wide application row took 273 pixels in total, leaving 643 for the path. Long paths, expanded sections and larger fonts still scrolled normally. The prototype also checked document width on all four pages at 320, 390, 620, 1100 and 1920 pixels.

west and CMake each used an empty build directory. Both tests followed the missing-board prompt into search, selected `qemu_cortex_m3`, configured and compiled an ELF. Checks covered Tab navigation, arrow keys on radio buttons, appearance preview and cancellation, appearance persistence across projects, and switching the host between light, dark, high-contrast light and high-contrast dark. Source and installed contents were compared. Native UI tests in this round ran on Windows.

### Implementation boundaries

`build_page` owns actions and missing-prerequisite entries on the build page. `build_view_state` retains expanded sections and focus per workspace, application, board, build directory and method. Prototype and extension share build controls, command rendering and styles. The prototype uses example data, while the extension reads real task arguments. The extension host constructs and executes tasks.

`workbench_appearance` manages preview, cancel and apply in the appearance dialog. `appearance_settings` writes only the selected appearance fields. Appearance changes also work without an open project and do not require rescanning devicetree, modules or tools. The prototype stores preferences in the browser.

| Scenario | Observed in VS Code |
| --- | --- |
| Windows, Chinese, existing build directory | Opened at Workspace. Navigation order was Build, Workspace, Project configuration and Modules. Workspace inherited Zephyr and SDK paths from the VS Code process, read board and toolchain from the target cache and identified each source. |
| CMake, existing cache | Built a `qemu_cortex_m3` ELF from local Zephyr 4.5.0-rc1 `hello_world`. After applying `CMAKE_BUILD_TYPE=MinSizeRel`, the build page still showed the previous `Debug`. Clicking Configure updated both the on-disk cache and UI to `MinSizeRel`. |
| Windows, English, new build directory | Before first configuration the board, CMake `-G Ninja`, explicit `OFF`, `0` and an empty string were visible. Workspace and Build both indicated which values already had a source. |
| west workspace | Writing west `build.generator` in an isolated test workspace made the UI show `Ninja Multi-Config` and its source. The board matched `-b`. This case verified reading configuration. |
| Switch application or build directory | Regression cases cover another app, another board, a copied cache and a cache lacking identifying metadata. Cached board defaults and variables apply only to their matching target. |

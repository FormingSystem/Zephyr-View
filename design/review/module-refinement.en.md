# Module review after the Build page

[简体中文](module-refinement.md) | **English**


The Build page was delivered first. The second delivery fixed target ownership in Workspace and the debug sidebar (W1 and D1), with two-root testing in a separate Windows VS Code development host. The initial offline reproductions of two module synchronization issues are retained below. Each item identifies the verified scope and remaining test conditions.

## Order of work

| Order | First user action | Delivery scope |
| --- | --- | --- |
| 1 · Build | Select application and board, configure, build and confirm available tools and actual inputs. | Follow the current build-specific acceptance record. Review and commit subsequent work separately. |
| 2 · Workspace, manifest and modules | Check the runner after switching target, find imported manifest projects, resume interrupted sync. | Resolve wrong targets, missing projects and unclear partial execution first. |
| 3 · Environment and debugging | Set up a new machine, resolve multiple local candidates and select the debug project in a multi-root workspace. | Explain scope and prerequisites where the action runs. Retain native directory selection and debug views. |
| 4 · Project configuration and appearance | Locate a node, distinguish drafts from build results, adjust theme and sidebar. | Reuse validated graph, save and build interfaces, then consolidate duplicate displays. |

Offline `west list -f "{name}"` returns `manifest` and `imported-module`. The project graph's direct manifest reader and `modules.entries` return empty lists. Per-item results must remain accurate if the second checkout changes after preflight. After resolving changes, retry only unfinished items, preserve manifest revisions and avoid downloading successful items again. |
| **M3 · Medium · Confirmed in code.** On a new workspace, selecting an application and board loads the mode's saved module selections. ## Revalidation and delivery

For each change, record the platform, language, input project, board, build directory, actual actions and results. Desktop screenshots are 1920×1080 and show both target and outcome. Test installation behavior with the real VSIX and record pure-data regressions and prototype screenshots separately. Physical probes, Linux package installation and private remote credentials each need tests in their own environment. When an item passes, update its dedicated review, the user guide and this table. Keep other items open until their own criteria pass.

**English summary.** The build screen was followed by the workspace and sidebar target fixes. A Windows VS Code 1.147.0 development host with two workspace folders retained the selected project across webview and terminal focus. An actual debug session selected its owning folder and left it active after termination. A real `mps2/an386` build reported its generated `pyocd` runner until a different board was selected. The appearance dialog can restore VS Code theme tracking. Module error localization, imported project visibility and recovery from partial synchronization remain open.

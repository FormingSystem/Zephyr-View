# Multi-architecture builds and configuration file discovery

[简体中文](multi-board-build.md) | **English**

This page records 0.5.14 behavior. Since 0.5.15, the user confirms whether to use a lone nonstandard `.conf`. The [standard adaptation checklist](standard-adaptation.en.md) describes the full rules and newer build results.

Tested on 2026-11-26 with Windows x64, Zephyr SDK 1.0.1 and west 1.5.0. The general-purpose targets used Zephyr 4.5.0-rc1. HC32F4A0PITB used the 4.4.99 checkout providing that board and the local `cmsis_6` and `hal_xhsc` modules. All applications, SDKs and modules came from local storage.

### Boards and target architectures

Each row produced a `zephyr/zephyr.elf` in its own build directory. Before configuration, the test invoked the extension's devicetree detection and file selection interfaces. It compared each path and its order with what Zephyr ultimately wrote to `build_info.yml`. After configuration, the extension read the build directory again to check the board defaults, application configuration and overlays. Finally, the test checked the target architecture in the ELF header.

| Board / SoC / CPU | Build method | Parallel host jobs | Automatically selected devicetree | ELF architecture |
| --- | --- | --- | --- | --- |
| `uyup_rpi_a/hc32f4a0pitb` | CMake | 1 | `uyup_rpi_a_hc32f4a0pitb.dts` | ARM |
| `mps2/an386` | CMake | Auto (32) | `mps2_an386.dts` | ARM |
| `nrf5340dk/nrf5340/cpuapp` | west | Auto (32) | `nrf5340dk_nrf5340_cpuapp.dts` | ARM |
| `nrf5340dk/nrf5340/cpunet` | CMake | 4 | `nrf5340dk_nrf5340_cpunet.dts` | ARM |
| `qemu_x86/atom` | west | 2 | `qemu_x86.dts` | Intel 80386 |
| `qemu_riscv32/qemu_virt_riscv32/smp` | CMake | 3 | `qemu_riscv32_qemu_virt_riscv32_smp.dts` | RISC-V |

All six targets used their board `*_defconfig` and the application's `prj.conf`. Both build methods rebuilt from clean directories using the parallelism arguments generated by the extension. The host reported 32 available logical processors. The RISC-V `.config` included `CONFIG_SMP=y` and `CONFIG_MP_MAX_NUM_CPUS=2`, while the host ran three compile jobs. The two nRF5340 CPUs each compiled to a separate image. This run covered compilation and linking. It did not flash hardware.

### Multiple files in the application

Two further Intel Atom builds used isolated application copies. Each checked the inputs recorded by Zephyr and the effective values in `.config` and `zephyr.dts`.

| Action | Inputs in merge order | Result |
| --- | --- | --- |
| Automatic configuration with `operator.conf` and a root-level `app.overlay` also present | `prj.conf` → `socs/atom.conf` → `boards/qemu_x86_atom.conf`, then `socs/atom.overlay` → `boards/qemu_x86_atom.overlay` | west produced an Intel ELF with stack size 3584 and devicetree model `board-default` |
| Selected two configuration fragments and one overlay in the extension | `first.conf` → `last.conf`, with `explicit.overlay` | CMake produced an Intel ELF with stack size 3072 and devicetree model `matrix-picked` |

### Checking the x86 Python dependency

The same Python module was available from two sources on the host. Zephyr's `scripts/dts/gen_edt.py` puts the checkout's `scripts/dts/python-devicetree/src` first in its search path when writing `edt.pickle`. The x86 script `arch/x86/gen_mmu.py` appends the source path. When reading that file back it found `devicetree/edtlib.py` from the local virtual environment's `dtsh 0.2.5` first. This copy lacked `_LocalProps` and x86 page-table generation failed. The devicetree package bundled with Zephyr declares its `PyYAML>=6.0` dependency in `scripts/dts/python-devicetree/setup.py`.

The repeat test used a separate Python 3.12 virtual environment, reused the remaining installed dependencies, installed the checkout's `devicetree 0.0.2` into the new site-packages offline, and confirmed the imported file came from the new environment. After clearing `PYTHONPATH` for the test process, CMake and west each configured `qemu_x86/atom` in an empty build directory. Both used the new interpreter, generated page tables and linked an Intel 80386 ELF.

If you encounter this conflict, run the following commands from the matching Zephyr checkout in a dedicated Zephyr development virtual environment. Install setuptools and PyYAML beforehand for offline installation.

```sh
python -m pip install --no-index --no-build-isolation --no-deps ./scripts/dts/python-devicetree
python -c "from devicetree import edtlib; print(edtlib.__file__)"
```

### Repeating the tests locally

The released VSIX also passed UI checks in Windows VS Code. Typing `dmcp` under Application configuration found `demo-copy.conf` and retained existing selections. Selecting the same file in the Windows file picker and then restoring project settings restored the original `prj.conf` and build readiness. The application configuration node in the configuration graph offers the same actions. Changing parallel jobs from automatic (32) to a custom value of 3 immediately showed `--parallel 3` in the CMake preview. [Installed build page at 1920 × 1080](installed/configuration-inputs-0.5.14.png)

Use a fresh build directory in the Zephyr checkout to check a target. These examples use the SDK's x86 and RISC-V toolchains. Change the build directory as well when switching to another target in the table. For HC32, build from a checkout containing `uyup_rpi_a` and supply its required modules through the west manifest or CMake's `ZEPHYR_MODULES`.

```sh
west build --cmake-only -b qemu_x86/atom -d build/matrix-x86 samples/hello_world
west build -d build/matrix-x86 -o=-j2
cmake -S samples/hello_world -B build/matrix-riscv -G Ninja -DBOARD=qemu_riscv32/qemu_virt_riscv32/smp
cmake --build build/matrix-riscv --parallel 3
```

Run the tests in a development terminal that can build Zephyr. Set `ZEPHYR_BASE` to the checkout under test and make the Python environment, SDK, Ninja and required modules available. The following script lives in the independent extension project. It keeps the application, artifacts referenced in build logs and configuration records in the system temporary directory. Each round checks input file contents byte by byte, the effective stack size and the ELF, and prints the directory for inspection.

```sh
node tests/integration/build-file-selection.cjs mps2/an386
```

For `mps2/an386`, successive builds in the same directory produced stack sizes of 1536 (default), 3072 (`first.conf;last.conf`), 2048 (order reversed) and 1536 (default restored). After selecting a replacement base devicetree and an overlay, the hardware model became `selected-overlay`. Restoring automatic selection selected `mps2_an386.dts` again and restored the original model. A separate application with only `application.conf` automatically built with a stack size of 2304. All seven runs checked the actual input order in `build_info.yml`, final `.config`, ELF and source file contents. Change the board target at the end of the command to repeat with other installed toolchains. [Validation script](../../tests/integration/build-file-selection.cjs)
